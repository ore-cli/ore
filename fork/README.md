# `fork/` — ore fork infrastructure

`ore` is a long-lived, rebranded fork of [openai/codex](https://github.com/openai/codex) that tracks
upstream **stable** tags indefinitely. Everything in this directory exists to keep the *upstream diff
surface minimal*: additive over invasive, new files over edits, generated over hand-merged.

Nothing here ships to users. `fork/**` is excluded from the substitution pass and from release artifacts.

## Topology

```
delta   ordered series of small, single-purpose commits on a pinned upstream tag.
        Each commit carries an intent header (Fork-Patch/Purpose/Invariant/Verify/Conflict-notes).
        This branch is hand-authored and reviewed; it never contains generated output.

main    GENERATED by CI: upstream tag -> apply delta series -> generated passes -> verify.
        Every sync lands as ONE merge commit whose parents are (previous main, upstream tag),
        so main is append-only and upstream history is reachable. Never commit to main by hand.

tags    ore-v*, ore-zsh-v*, ore-rusty-v8-v*  — the ONLY tags ever pushed to origin.
```

Assembly order (see `fork/assemble.sh`): series first on the pristine tag, then the generated passes.
Substituting before rebasing would rewrite the context every series hunk anchors on, exploding conflicts
and invalidating every `git rerere` record.

## Tag policy — upstream-name tags are NEVER pushed

Upstream's workflows ride along in the tree and **run from the tree of the pushed ref**. Pushing an
upstream-named tag to `origin` therefore executes upstream-authored CI that this fork has not
neutralized:

| Tag pattern | What happens if pushed |
|---|---|
| `rust-v*` | `rust-release.yml` (no repository guard) starts the full build matrix, burns runner minutes, then dies on OpenAI-private infrastructure |
| `codex-zsh-v*` | `rust-release-zsh.yml` **publishes a real GitHub Release** under upstream's asset names |
| `rusty-v8-v*` | `rusty-v8-release.yml` builds V8 for hours and may **publish a real Release** |

Sidecar releases are triggered exclusively by fork-authored workflows on `main` with ore-prefixed tags:
`ore-v*`, `ore-zsh-v*`, `ore-rusty-v8-v*`. Upstream tags are fetched into a non-tag namespace
(`refs/upstream/tags/*`) so even a reflexive `git push --tags` has nothing upstream-shaped to push.
Four layers enforce this: the fetch namespace, `safe_push()` in `fork/lib.sh`, the `fork/verify`
workflow check, and a server-side tag ruleset with an empty bypass list.

## Why the invariants must test `--release` builds

Upstream suppresses the Statsig metrics exporter under `cfg!(debug_assertions)`
(`codex-rs/otel/src/config.rs`). A debug build therefore never transmits, **whether or not the fork's
telemetry patches are present** — a debug-green egress run proves nothing. `fork/verify/run.py`
refuses debug binaries for the egress and binary-strings suites.

## First-push sequence (one time, in this order)

1. Make `ore-cli/ore` public (GitHub Free cannot configure Environments on private repos; npm
   provenance, SignPath and Sigstore identity also assume public).
2. Disable Actions for the repository.
3. Install the tag ruleset: restrict *creation* of `rust-v*`, `codex-zsh-v*`, `rusty-v8-v*`,
   `python-v*`, `artifact-runtime-v*`, `codex-rs-*` with an **empty bypass list**.
4. Push `delta` and the assembled `main` (branches only — never `--tags`).
5. Set the default branch to `main`.
6. `gh workflow disable` every upstream-authored workflow.
7. Re-enable Actions with only the fork workflows active.

Step 6 is load-bearing and is **not** replaced by the assemble-time relocation: relocation cleans
`main`'s tree, but `delta`'s tree still carries live upstream workflow files. Repository-level
disablement is the ref-independent guard. `fork/verify/workflows_check.py --api` asserts that the set of
enabled workflows equals the fork allowlist; the sync workflow disables any newly-arrived upstream
workflow before finalizing.

## Versioning

ore uses scheme **C**: `1.{upstream_minor}.{ore_patch}`. Base `rust-v0.149.0` → `ore-v1.149.0`;
fix releases `1.149.1`, `1.149.2`, …; next base `rust-v0.150.0` → `1.150.0`. `fork/VERSION` is the single
source of truth — `assemble` writes `[workspace.package] version` from it (never a series edit) and
auto-derives the minor on a new base tag; `fork/verify/version_check.py` blocks a sync when
`minor(fork/VERSION) != minor(UPSTREAM.tag)`.

Rationale: `CARGO_PKG_VERSION` is wire-visible (`User-Agent: codex_cli_rs/<ver>`,
`/models?client_version=`), and the backend gates model availability on `minimal_client_version`. A `0.x`
line would present as an ancient client; `1.149.x` clears every published gate. The exact upstream base is
never lost — it is reported on line 2 of `--version` and recorded in `fork/UPSTREAM`.

`ore --version` (long form):

```
ore 1.149.0
codex-base: rust-v0.149.0 (758ef40f50)
```

Line 1 must remain exactly two tokens: `codex-app-server-daemon` compares
`--version`'s second whitespace token against `CARGO_PKG_VERSION`, and the installers match the trailing
token of the first matching line. Line 2 deliberately ends in `)` so it can never be mistaken for a
version.

## Entrypoint naming

The shipped CLI is `ore`; the cargo target stays `codex`. The rename happens at packaging time
(`scripts/codex_package/targets.py` `executable_stem`), which keeps 46 `cargo_bin("codex")` test sites,
the Bazel graph and `cargo run --bin codex` untouched. The `[[bin]] name = "ore"` alternative (plus a
`codex-rs/utils/cargo-bin` alias, five Bazel labels and an entitlements rename) is documented as a
fallback should `cargo install` UX ever require it.

## Directory map

| Path | Purpose |
|---|---|
| `UPSTREAM` | machine-readable base manifest (tag, peeled commit, tag object, dates) |
| `VERSION` | ore semver line (scheme C) |
| `substitutions.yaml` | rebrand rules as data — display strings, URLs, package names; regenerated every sync |
| `substitute.py` | substitution engine (`--apply` / `--check` / `--audit` / `--list`) |
| `workflows.allow` | the only workflow basenames allowed to remain live |
| `assemble.sh`, `lib.sh` | tag → main pipeline and shared shell helpers (`safe_push`) |
| `relocate_workflows.py` | deny-by-default relocation of upstream workflows into `fork/upstream-workflows/` |
| `verify/` | the invariant suite (`run.py` + checks + data files) |
| `release/` | release scripts upstream deleted or never had (rcodesign notarization, Homebrew renderer) |
| `sync-notes.md` | measured cost of a real upstream hop, and the verify red-team |
| `upstream-workflows/` | generated on `main` only; byte-identical copies of relocated upstream workflows |

## Working on the series

```sh
git switch delta
# ... author a commit with the full intent header ...
fork/lint-series.sh          # trailers, unique slugs, forbidden paths
fork/verify/run.py --suite static
```

Series commits must never touch `codex-rs/Cargo.lock`, `MODULE.bazel.lock`, `pnpm-lock.yaml`, generated
schema fixtures (unless the same commit changes their generator inputs), or `fork/upstream-workflows/`.
Lockfiles are regenerated by `assemble`, never hand-merged.

## Fork-owned environment variables

| Variable | Effect |
|---|---|
| `ORE_HOME` | ore's config/state home. Wins over `CODEX_HOME`; default `~/.ore`. |
| `CODEX_HOME` | Honored as a full alias for `ORE_HOME` — upstream-pure mode. Setting it also suppresses the legacy `~/.codex` base layer and the one-shot auth import, because a caller who pinned a home explicitly (every test harness, the SDK suites, `logs_client`, the doctor's child process) must see exactly that home and nothing layered underneath it. |
| `ORE_IMPORT_CODEX_CHATGPT_AUTH` | Opt in to importing ChatGPT tokens from `~/.codex/auth.json`, not just an API key. Off by default: refresh tokens rotate on use, so importing them makes two installs invalidate each other's session. |
| `ORE_CURATED_PLUGINS_REPO` | `owner/repo` of a curated-plugins repository to sync at startup. Unset means no sync — ore hard-codes no curated repository, so being unconfigured and being disabled are the same state. |

The one-shot auth import runs from the `ore` CLI entrypoint. Someone whose first
contact with the fork is `codex-app-server` (an IDE integration) imports on their
first `ore` run instead.

## `codex-rs/Cargo.lock` on `delta`

Series commits may not touch it, so on `delta` the lock is upstream's and does
not list the crates the fork adds. The first cargo invocation in a checkout will
therefore update it; that is expected, and `ore-ci.yml` tolerates exactly that
one path being dirty on `delta` and nothing else. `assemble.sh` regenerates the
lock, so `main` is always in sync and gets the strict check.
